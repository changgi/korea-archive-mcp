# 기록잇다 (GIROK-ITDA)

> 누구나 발굴자가 된다 — 국내외에 흩어진 우리 기록을 국민이 직접 찾는 플랫폼

공공데이터·AI 활용 창업경진대회 아이디어 기획 부문 출품작.

---

## 무엇인가

국민이 일상 언어로 물으면, **어떤 기록이 필요한지 → 어느 기관에 있는지 → 어떻게 받는지**를 안내하고, 국내외 문서고를 동시에 검색해 실제 기록을 찾아주는 서비스입니다.

기존 기록 검색은 「지적원도」·「임야조사부」라는 정답을 이미 아는 사람에게만 작동합니다. 기록잇다는 그 정답을 몰라도 되게 만듭니다.

## 왜 필요한가

| 벽 | 국민이 겪는 상황 |
|---|---|
| 표기 | 같은 한국이 Korea·Corée·Chosen으로 흩어져 있어 한 표기로는 대부분을 놓침 |
| 체계 | 문서군·시리즈 코드를 모르면 검색창에 무엇을 넣을지 모름 |
| 용어 | 필요한 기록의 정식 명칭을 모름 |
| 소재 | 국가기록원·지자체·법원 중 어디 소관인지 모름 |
| 형태 | 찾아도 한자·손글씨·옛 서식이라 못 읽음 |

## 실행

별도 설치가 필요 없습니다.

```
# 파일을 브라우저로 열기
open index.html

# 또는 로컬 서버
python3 -m http.server 8080
```

배포는 정적 호스팅이면 무엇이든 됩니다. 빌드 단계가 없습니다.

## 구성

```
girokitda/
├── index.html          시연본 (단일 파일 · 의존성 없음)
├── api/overseas.js     해외 문서고 검색 프록시 (서버리스 함수)
├── test.js             검사 (90개 항목)
├── coverage.js         판단 범위 측정
├── consistency.js      산출물 정합 점검
├── package.json
├── .github/workflows/  코드가 바뀔 때마다 검사 자동 실행
├── vercel.json         배포 설정
└── README.md
```

`index.html`은 그 자체로 완결됩니다. 해외 실연동만 프록시가 필요합니다.

단일 파일로 만든 이유는 두 가지입니다. 심사위원이 링크 하나로 즉시 열어볼 수 있어야 하고, 어떤 기록관이든 파일 하나만 받아 자기 데이터로 고쳐 쓸 수 있어야 하기 때문입니다.

## 검사

판단 규칙과 응답 파싱이 의도대로 도는지 직접 확인할 수 있습니다.

```bash
npm install puppeteer      # 최초 1회
node test.js               # 90개 항목 (네트워크 불필요)
node test.js --net         # 95개 항목 (해외 문서고 실제 조회 포함)
node coverage.js           # 판단 범위 측정
DOCS_DIR=../docs node consistency.js   # 산출물 정합 점검
```

### 문서끼리 어긋나지 않는가

계획서·요약·발표자료·발표준비·부록·README·시연본에 같은 수치가 흩어져 있습니다. 한쪽만 고치면 반드시 어긋나므로 기계가 대조합니다.

대조하는 것: 표기 실측값이 여러 문서에 같게 적혔는가 · 수요 근거가 기준 시점과 함께 표기됐는가 · 문서가 말하는 검사 항목 수가 실제로 돌려본 수와 같은가 · 시나리오 수가 일치하는가 · 계획서가 내건 네 약속마다 대응하는 검사가 있는가 · 운영비를 구간별로 나눠 적었는가 · 영상 길이와 슬라이드 수가 실물과 맞는가 · 발표자 노트가 나중에 추가된 내용까지 담고 있는가 · 발표 대본이 모든 슬라이드를 다루고 시간이 끊기지 않는가 · **부록의 제출물 목록이 실제 파일을 빠짐없이 담았는가**.

실제로 이 점검이 잡아낸 것들입니다.

- **계획서에만 접근성 약속이 통째로 빠져 있었습니다.** 검사 15개가 확인하고 부록에도 적혀 있는데 정작 계획서 본문에 한 번도 등장하지 않았습니다.
- 부록이 슬라이드를 11장이라 적었으나 실제는 12장이었습니다.
- 영상 길이를 44초로 적었으나 실제는 43초였습니다.
- **부록 제출물 목록에 해외 검색 프록시가 빠져 있었습니다.** 국경 축을 떠받치는 핵심 파일인데 목록에 없었습니다. 판단 범위 측정과 자동 실행 설정도 마찬가지였습니다.
- **발표 대본에 차별성 슬라이드가 통째로 빠져 있었습니다.** 실측값이 실린 가장 강한 슬라이드인데 무슨 말을 할지 정해져 있지 않았습니다.
- **발표자 노트가 초기 상태로 남아 있었습니다.** 이후 추가한 표기 판별 실측·다섯 갈래·공동 발굴 대장·수요 근거·운영비가 하나도 반영되지 않아, 발표자가 노트를 보고 말하면 옛 내용을 말하게 될 상태였습니다.
- 점검기 자신도 틀렸습니다. 검사 수를 호출 지점으로 세어 80개로 잡았는데 실제 통과는 90개였습니다. 코드를 읽어 추정하는 대신 실제로 돌려서 세도록 고쳤습니다.

### 보류와 적중, 두 방향을 함께 봅니다

근거 없이 답하지 않는 것은 안전장치이지만, 답할 수 있는 질문까지 보류하면 도구가 쓸모없어집니다.

시험 문장을 사전과 같은 사람이 만들면 점수가 부풀기 때문에, 세 묶음으로 나눠 잽니다.

| 묶음 | 예 | 결과 |
|---|---|---|
| 쉬운 표현 | "지적원도 열람 신청" | 21개 중 21개 적중 |
| 어려운 표현 | "낳아주신 분을 찾고 싶은데 어디서 시작해야 할지" | 14개 중 14개 적중 |
| 범위 밖 | "진료기록 사본을 떼려고 합니다" | 6개 중 6개 올바로 보류 |

범위 밖 묶음이 중요합니다. 입양·의료·특허처럼 이 서비스가 다루지 않는 영역을 물었을 때 그럴듯하게 답하면 안 됩니다.

낱말 사전을 넓히면 적중률은 오르지만 보류가 무너질 수 있습니다. 실제로 이 측정에서 헛보류가 발견되어 사전을 두 차례 보완했고, 그때마다 보류 여섯 가지가 그대로인지 확인했습니다. 두 검사를 함께 돌려 어느 한쪽으로 기울지 않게 합니다.

검사하는 것: 해외 검색 프록시가 노이즈 표기를 걸러내고 중복을 제거하는가 · 네 갈래를 맞게 고르는가 · 근거가 없을 때 답하지 않는가 · 점수 규칙이 의도대로인가 · 검색어에서 군더더기를 걷어내는가 · 기관마다 다른 응답 태그를 읽는가 · 오류 응답을 오류로 처리하는가 · 표기 변형을 유효와 노이즈로 나누는가.

이 프로젝트의 두 가지 약속은 특히 촘촘히 검사합니다.

**근거가 없으면 답하지 않는다** — 여섯 가지 입력으로 확인합니다. 보류 규칙을 지우고 돌리면 다섯 항목이 즉시 실패합니다.

**개인 신상은 저장하지 않는다** — 공동 발굴 대장에 실제로 무엇이 담기는지 값으로 확인합니다. 개인 신상이 잔뜩 섞인 질의를 넣고, 저장 항목에 생년·본적·가족관계가 없는지, 허용된 항목 외에 다른 것이 섞이지 않았는지 봅니다. 본적 한 줄만 추가해도 두 항목이 실패합니다.

**접근성은 기본값이다** — 글자 크기·행간·이름표·키보드 이동·초점 표시·동작 최소화 존중을 값으로 확인합니다. 본문 글자를 13px로 줄이거나 초점 표시를 지우면 즉시 실패합니다.

**무엇이 실제이고 무엇이 구성인지 밝힌다** — 시나리오마다 출처를 표시하는지, 오키나와만 "실제 조사 재현"으로 되어 있는지, 구성한 것을 실제라고 하지 않는지 확인합니다.

원칙이 문서에만 남고 코드에서 사라지는 일을 막기 위한 장치입니다. GitHub에 올리면 코드가 바뀔 때마다 자동으로 돌아갑니다.

## 찾은 것이 쌓입니다

각자 검색하고 흩어지면 다음 사람은 다시 처음부터 시작합니다. 그래서 발굴 결과를 공동 대장에 남길 수 있게 했습니다.

남기는 것은 **사람이 아니라 기록의 소재**입니다. 소장기관·참조번호·시기·유효 표기가 다음 사람의 출발점이 됩니다. 이름·생년·본적 같은 신상은 어떤 경우에도 저장하지 않습니다.

무엇이 저장되는지 모른 채 누르는 단추는 두지 않았습니다. 단추를 누르면 저장될 내용 전문이 먼저 표시되고, 확인한 뒤 한 번 더 눌러야 등록됩니다.

## 시연 시나리오

화면의 예시 버튼이 각각 다른 이용자를 보여줍니다.

1. **오키나와에 끌려간 할아버지** — 해외 문서고에서 개인 신원을 찾는 경로
2. **돌아가신 아버지 명의 땅** — 재산관계 기록의 소관 판별과 신청 절차
3. **아버지 군 복무·학교 기록** — 병역·학적·제적이 세 기관에 나뉜 경우
4. **해외입양 친생부모 기록** — 입양기관·법원·입양국에 흩어진 기록
5. **사라지는 우리 동네 기록** — 지역 기록을 모아 전시로 잇는 경로
6. **막연하게 물어보기** — 판단이 서지 않을 때의 동작

## 모르면 모른다고 말합니다

다섯 번째 버튼이 이 프로젝트의 핵심 설계를 보여줍니다.

행정 안내에서 틀린 정보는 국민에게 실제 손해를 줍니다. 그래서 질문의 근거가 부족하거나 두 갈래가 팽팽하면, **답을 지어내지 않습니다.** 조회표 도장이 `확인필요`로 바뀌고, 가까운 갈래를 되묻거나 담당기관 연락처를 안내합니다.

판단 규칙은 `route()`에 있습니다. 낱말별 가중치를 더해 최고점이 기준에 못 미치거나, 1·2위 차이가 좁으면 `null`을 반환합니다. 정식 서비스에서는 언어모델이 같은 판단을 하되, 확신이 없으면 답하지 않는다는 원칙은 동일합니다.

## 시연본과 정식 서비스

현재 화면은 **실제 발굴 과정을 재현한 시연본**입니다. 응답 데이터는 `index.html` 안의 `DATA` 객체에 들어 있습니다.

정식 서비스에서는 이 자리에 실시간 연동이 들어갑니다.

| 구간 | 시연본 | 정식 서비스 |
|---|---|---|
| 의도 해석 | 핵심어 규칙 (`route()`) | 언어모델 기반 분류 |
| 기록 검색 | 재현 데이터 | 이용자가 넣은 기관 오픈API 주소로 실시간 조회 |
| 해외 검색 | 재현 데이터 | **구현 완료** — `api/overseas.js` 프록시 경유 |
| 필름 판독 | 판독 결과 재현 | 원격 스트리밍 판독 엔진 |
| 절차 안내 | 검증 템플릿 | 검증 템플릿 (동일) |

교체 지점은 코드에 주석으로 표시해 두었습니다.

## 설계 원칙

**오답을 만들지 않습니다.** 행정 안내에서 틀린 정보는 국민에게 실제 손해를 줍니다. 그래서 세 겹으로 막습니다.

1. 절차 안내는 사전 검증된 템플릿에서만 조립합니다
2. 검색 결과는 실제 API 응답만 표시합니다
3. 근거가 없으면 답을 만들지 않고 담당기관 연락처를 안내합니다

**기록을 각색하지 않습니다.** 서술은 기록 원문에서만 가져오고, 기록의 공백은 공백이라고 표시하며, 권리등급을 확인한 뒤에만 사용합니다.

**단정하지 않습니다.** 동명이인 가능성이 있는 한 신원을 확정하지 않고, 대조가 필요한 항목을 함께 안내합니다.

## 접근성

재산·신분 기록을 찾는 이용자는 상당수가 고령층입니다.

- **말로 입력할 수 있습니다.** 마이크 버튼을 누르고 말하면 됩니다. 말이 끝나면 자동으로 검색합니다. 지원하지 않는 기기나 마이크가 없는 환경에서는 버튼이 아예 나타나지 않습니다.
- 기본 글자 크기를 키우고 행간을 넓혔습니다
- 모든 문구의 명암비를 실측해 WCAG AA를 충족합니다 (본문 14.5:1, 보조 문구 4.87:1 이상)
- 키보드 초점이 항상 보입니다
- 동작 최소화 설정을 존중합니다 (`prefers-reduced-motion`)
- 모바일 세로 화면을 우선으로 설계했습니다
