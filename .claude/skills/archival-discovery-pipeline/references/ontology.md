# 메타데이터 구조화와 온톨로지

재기술 결과를 **기계가 읽을 수 있는 형태**로 만든다.

## 왜 구조화하는가

재기술이 문서 안에만 있으면 **그 한 건에서 끝난다.**
구조화하면 여러 건을 이어 붙일 수 있고, 관계 발견의 입력이 된다.

```
문서만 있을 때:  "이 필름은 1948년 제주에서 SHAYDAK이 찍었다"
구조화한 뒤:     "SHAYDAK이 찍은 다른 필름은?"
                 "같은 부대가 다른 지역에서 찍은 것은?"
                 "같은 사건을 다른 시점에서 담은 것은?"
```

## 채택한 표준 셋

| 표준 | 무엇에 쓰는가 |
|---|---|
| **RiC-O** | 기록 기술 — 국제기록평의회 Records in Contexts |
| **CIDOC-CRM** | 사건 중심 모형 — 문화유산 정보 참조 모형 |
| **Dublin Core** | 최소 교환 — 기관 간 단순 연계 |

**RiC-O와 CIDOC-CRM을 함께 쓰는 이유**가 있다.
RiC-O는 「이 기록이 무엇인가」를, CIDOC-CRM은 「무슨 일이 있었는가」를 다룬다.
발굴 자료는 둘 다 필요하다 — 기록물이면서 동시에 사건의 증거이기 때문이다.

### 주요 매핑

| 우리 개념 | RiC-O | CIDOC-CRM |
|---|---|---|
| 기록(필름) | `rico:Record` | `crm:E31_Document` |
| 촬영자 | `rico:Agent` | `crm:E39_Actor` |
| 촬영 부대 | `rico:Group` | `crm:E74_Group` |
| 장소 | `rico:Place` | `crm:E53_Place` |
| 사건 | `rico:Event` | `crm:E5_Event` |
| 촬영일 | `rico:hasCreationDate` | — |
| 기록 대상 | — | `crm:P70_documents` |

### 로컬 확장 (`kad:`)

표준에 없는 것은 자체 네임스페이스로 낸다. **이것이 이 파이프라인의 특징이다.**

| 속성 | 내용 |
|---|---|
| `kad:hasReading` | **판독 근거** — 시각·대상·방법·신뢰도 |
| `kad:confidence` | 신뢰도 등급 |
| `kad:basis` | 확정의 근거 (슬레이트·표지판 등) |
| **`kad:unconfirmed`** | **확인하지 못한 것 — 이것도 데이터다** |
| `kad:publicationTier` | 게재 판정 단계 |
| `kad:tentativeDate` | 신뢰도가 낮은 날짜 |

**`kad:unconfirmed`가 중요하다.**
「무엇을 모르는가」가 기계 판독 가능한 형태로 남아야,
다음 연구자가 그 지점을 이어받을 수 있다.

## 신뢰도 필터

**모든 판독이 같은 무게를 갖지 않는다.**

| 등급 | 온톨로지 처리 |
|---|---|
| 확정 | 확정 속성으로 내보냄 |
| 높음 | 확정 속성으로 내보냄 |
| **부분** | **`kad:tentative*` 로만 — 그래프에 싣지 않음** |
| **불가** | **판독 기록에만 남기고 개체로 만들지 않음** |

이 필터가 없으면 추정이 사실처럼 그래프에 들어간다.
**한번 그래프에 들어간 오류는 관계 추론을 통해 증폭된다.**

## KARDA 연동

관계 발견 에이전트의 입력으로 쓸 노드·엣지를 낸다.

```bash
python scripts/make_metadata.py karda <판독.json> --out <디렉터리>
```

### 노드 유형

| 유형 | 예 |
|---|---|
| `record` | 111-ADC-7115 |
| `place` | 제주 |
| `agent` | SHAYDAK |
| `unit` | FE Signal Corps |
| `event` | 미소공동위원회 |

### 엣지 유형

| 관계 | 뜻 | 판정 근거 |
|---|---|---|
| `sibling_of` | 자매편 | 동일 과제·연속 릴 |
| `precedes` / `follows` | 선행·후행 | 시간순 |
| `same_event` | 동일 사건 | 같은 사건의 다른 시점 |
| `same_agent` | 동일 촬영자 | 슬레이트 일치 |
| `same_unit` | 동일 부대 | 슬레이트 일치 |
| `same_place` | 동일 장소 | 판독된 지명 |
| `series_of` | 계열 | 같은 계열 |
| **`corrects`** | **정정** | **원 기술의 오류를 바로잡음** |

**모든 엣지에 `basis`와 `confidence`를 붙인다.**
관계가 어떤 근거로 성립하는지 남지 않으면 검증할 수 없다.

### 관계 발견의 실제

노드·엣지가 쌓이면 이런 질의가 가능해진다.

```
· 같은 촬영자가 다른 과제에서 찍은 것은?
    → 촬영자의 이동 경로가 드러난다
· 같은 부대가 여러 지역에서 찍은 것은?
    → 부대의 작전 범위가 드러난다
· 같은 사건을 다른 시점에서 담은 기록은?
    → 사건의 전개가 복원된다
· 자매편 관계가 끊긴 곳은?
    → 미공개·소실 자료의 위치가 드러난다
```

**마지막 질의가 특히 값지다.** ROLL 1·3이 있는데 2가 없다면,
그 자료를 열람 신청 대상으로 특정할 수 있다.

## 작업 순서

```bash
# ① 필수 항목 검사 — 「확인하지 못한 것」이 비어 있으면 경고
python scripts/make_metadata.py check <판독.json>

# ② 전부 변환
python scripts/make_metadata.py build <판독.json> --out <디렉터리>
```

산출:
- `metadata.jsonld` — RiC-O + CIDOC-CRM
- `karda_nodes.csv` · `karda_edges.csv` — 관계 발견 입력

## 판독 JSON 작성 요령

### 반드시 넣을 것

```json
"readings": [
  {"time": 12, "target": "slate",
   "text": "DATE 4/30/48 ...",
   "method": "VLM 3회 교차 + 형식 검증",   ← 재검증 가능하게
   "confidence": "확정"}
]
```

**`method`가 없으면 검사에서 걸린다.** 어떻게 읽었는지 남지 않으면
다음 사람이 그 판독을 신뢰할 근거가 없다.

### 실패도 기록한다

```json
{"time": 185, "target": "벽보",
 "text": "(손글씨 한글 5장 이상)",
 "method": "VLM·OCR 모두 불일치",
 "confidence": "불가"}
```

**판독 실패는 「없음」이 아니라 「불가」다.**
그 자리에 무언가 있었다는 사실 자체가 정보이며,
고해상도 재판독의 대상이 된다.

### 관계는 근거와 함께

```json
"relations": [
  {"type": "sibling_of", "target": "111-ADC-7114",
   "basis": "동일 과제 FEC 67"}
]
```

`basis` 없는 관계는 주장이지 데이터가 아니다.
